# map-procedural-generation — rules

Combine with the root CLAUDE.md. This is the **content / assembly** stage: it consumes the base terrain from `../map-procedural-generation-terrain/` (THE standalone base terrain generator) and CHUNKS its big `all.tmx` into per-map **zstd**-base64 `.tmx`, then adds cities/roads, reciprocal borders + doors, NPCs/trainers/signs, wild-encounter tables and interiors (heal / shop / gym). Full on-disk spec = `target.md`; per-datapack tile/item/skin config = `settings*.ini` + `DATAPACK-CONFIG.md`; what is left to do, and which part needs DRAWN art instead of code = `TODO.md`.

* **The generator NEVER writes your config.** `main()` copies the settings file to `settings-run.ini` and opens QSettings on THAT: `putDefaultSettings` adds any key the file lacks, and QSettings then rewrites the whole file, stripping every comment out of the checked-in `settings.ini`. Adding a new default is therefore free — do not "fix" this by dropping the copy.
* **`[road] extraSpacePercent{Min,Max,Variance}`** decide how much of a ROAD chunk is filled with walkable content beyond the path joining its borders (simple track ↔ chunk-filling grass/water). Rolled once per chunk, triangular so the middle of the range is the common case. City chunks are excluded on purpose: there every surviving zone becomes buildable ground, so filling/pruning would change how many buildings a town gets.
* Output is a STAGING tree at `<binary>/dest/map/main/<maincode>/` — NEVER the source datapack (`CatchChallenger-datapack/` is read-only). `cities.txt`/`dialog.txt`/`template/`/`skin/` load from the BINARY directory (CMake stages them there); settings come from `settings.ini` (or `--config settings-reference.ini`).
* **The output is ONE self-contained map LABEL: it SHIPS its own `tileset/`.** `dest/map/main/<maincode>/` is copied under `map/main/<label>/` of a datapack (`install-generated.py <dest> --datapack <dir> [--label <name>]`, label auto-detected from the run, which refuses to install while a reference escapes the label, and skips the `all.tmx` debug dump). So every written reference is `../tileset/x.tsx` — NEVER `../../../tileset/` (the datapack `map/tileset/` is read-only AND owns none of the gym/heal/shop/house sheets: that copy loaded with no tileset at all). `dest/map/tileset/` + `dest/map/main/tileset/` stay the RUN-STAGING POOL (`--datapack` fills them, `stageTemplateTileset` adds the template ones); `LoadMap::shipTileset` copies out of the pool at WRITE time, so an unused tileset is never shipped. `check-generated.py` enforces it.
* **Every CHUNK draws from its OWN random stream** (`LoadMapAll::seedChunk`, called first thing in each chunk-local pass with its `ChunkPass` id). Changing how many `rand()` a chunk consumes then shifts THAT chunk only, not the whole world — a diff stays readable and a regression stays local (measured: one extra `rand()` in one chunk touches 6 files out of 647, all of that chunk). NEVER reseed the global height/moisure/voronoi noise per chunk — it is global by construction and would tile the world. `check-determinism.py <build dir>` proves two runs stay byte identical; run it after any generator change.
* **RIGID rectangular grid-aligned features** (root + terrain CLAUDE.md): the terrain generator shapes the grass/feature zones; FILL them solid, NEVER thin a zone with per-cell noise to look "natural" (the `doc/mapping/Badmap.png` mistake — reverted once already).
* **Build/run OUT OF THE BOX:** `cmake -S . -B <build> && cmake --build <build> && <build>/map-procedural-generation` — clone, compile, run, NO argument. The `map-procedural-generation-runtime` target (always built) stages `template/ skin/ tileset/` and the txt/ini inputs next to the binary (a POST_BUILD command would only run when the binary relinks, so a template edit would never reach the build dir), and `LoadMap::stageTilesetPool` fills `dest/map/tileset/` + `dest/map/main/tileset/` from that `tileset/` at startup. Optional `--datapack <dir>` stages a datapack's tilesets FIRST, so they win over the tool's own copy of the same file name. ~32 s for 83 cities / 647 maps; repeated runs are byte identical. `[General] cleanTileset` (default true) drops the pool entries no map referenced once the run is over.
* **WALKABILITY GUARD, check AND repair** (`LoadMapAll::checkWalkability`, run on the finished world before a single file is written). Rule 1: all border openings of a chunk must be mutually reachable — a CAVE chunk is the exception, there they are meant to be separated and each one only has to reach the cave mouth on its own side (that is what forces the player through the corridor). Rule 2: every building door must be in the BIGGEST walkable component of its chunk. A failure is first REPAIRED (`carveChunkCorridor`: cheapest path with blocked cells costing 60x an open one, so the notch is narrow and follows the existing ground; it clears the Collisions and whatever hangs above the player, and fills the ground with the tile the chunk already uses), then re-measured; only what survives is reported, and then nothing is generated at all. Walkable follows the engine: blocked = ANY layer named `Collisions` holds a tile; water and ledges are passable. Object rows: door/teleport/border objects sit ON their cell, the −1 row offset is a BOT rule only.
* **VERIFY by rendering** (vision): maps are **zstd** base64 (`Base64Zstandard`, everywhere: chunks, interiors, all.tmx) — a renderer without zstd shows all-black. Use a zlib tileset renderer that follows each map's own relative `<tileset source>` (they resolve inside the label, `dest/map/main/<maincode>/tileset/`). A city must read as a town (HEAL/SHOP/gym buildings, grid trees); roads carry rigid grass blocks.
* **A skinned bot must stand on a FREE cell** (no `Collisions`, no `WalkBehind` above it, no second bot): vegetation is brushed LAST, so city townsfolk are placed after it (`main.cpp`) and road bots mask a ±2 ring (`maskVegetationAround`, like the signs). A bot with NO skin is a marker on a decor tile (sign, heal machine) and is a collision on purpose. `check-generated.py` enforces it.
* **Content quality:** NPC/trainer `<name>` come from an invented neutral name pool in `botStepXml` (LoadMapRoad.cpp), NOT the numeric bot id; flavor NPC lines come from `dialog.txt` (original themed sentences, not Lorem-Ipsum). `target.md` §2.1 = the region / location / `building/` naming taxonomy (real name → type fallback `city-N`/`cave-N`/`road-N`; isolated interiors under one `building/`; multi-region split by name/graph/`region-N`).
* **NEVER any franchise wording** in a generated text nor in a `template/` skeleton: the world is ORIGINAL. Generic English words are fine (Mart, Hospital, Gym). The word list is operator-local (`~/.config/CatchChallenger/franchise-denylist.txt`, loaded by `franchise_denylist.py`) — it must NOT be committed, it is made of the very names we may not carry. `npcfill.py` filters the model output, `check-generated.py` re-checks the whole tree, `template-check.py` re-checks the skeletons (the per-city rewrite hides them otherwise). No list on the machine = check skipped with a notice.

# Building templates (`template/<group>/`)

Every city building comes from a template FOLDER, discovered on disk (`LoadMapBuilding.cpp`), never hard-coded: one exterior tmx (brushed on the city ground) + `floor-N.tmx` interiors + `floor-N.xml` **content skeleton**. A group is either one folder per variant (`sea-city/1`..`7`) or the files directly (`shop-small`).
* Groups used: `heal-{small,medium,big}` and `shop-{small,medium,big}` picked by CITY SIZE, `gym-building` (non-small cities, keeps its historical shape: the template's fight bot is the LEADER, `[building] gymTrainers` extra trainers are injected on free cells and removed from the shared template afterwards), and one `*-city` STYLE group per city for the filler houses. Output names: `heal/shop/gym/house-N.tmx`+`.xml` (multi-floor → folder + `floor-N`).
* **A city STYLE may ship its own key buildings** (`LoadMapAll::cityBuildingSet`, stem = the style folder without `-city`): `desert-market-heal` (ONE building holding both the shop and the heal bot → written as `market-heal`) beats `desert-market`+`desert-heal`, which beat `desert-market-<size>`+`desert-heal-<size>`, which beat the generic `shop-<size>`+`heal-<size>`; `desert-gym` beats `gym-building`. `desert-special-building` is spawned per its own `how-use.ini`. Nothing to declare — the folders are looked up on disk, so dropping `template/desert-market/` in is all it takes.
* **`template/on-<what>/<name>/` = a DECORATION, not a building** (`scanDecorationTemplates` + `addTerrainDecorations`). `<what>` is either **`walkable`** — the GENERIC group, any cell the player can stand on whatever the terrain — or a `[terrain]` name (`on-water`, `on-mountain`…), for what goes where nothing walks. Each VARIANT folder carries its own `how-use.ini`. It is only brushed — no door wired, no interior written — so `scanBuildingTemplates` skips `on-*` on purpose. A copy lands only where every cell of its footprint qualifies (walkable / that terrain), free of `Collisions`/`WalkBehind`, outside every `cityBuildingRects` and off any object cell (a canopy over a trainer is a `check-generated.py` error). **The decoration ITSELF may be a collision** (a tree trunk): what has to be free of collision is the ground under it. It runs BEFORE the vegetation and masks its own footprint.
* **`how-use.ini` `terrains=` is a list of OR rules**, each `<terrain>` or `<terrain>-><neighbour>`: on that terrain, TOUCHING that other one. `terrains="sand->water;sand->grass;grass"` = sand by the water, or sand by the grass, or grass anywhere. A name matches as a PREFIX (`sand` covers `sand2`); TOUCH is measured 2 tiles out, because between two zones there is always the 1-tile band of transition tiles. **A `;` MUST be quoted** — QSettings reads an unquoted one as a comment and drops the rest of the line; `readTemplateUse` says so on stderr rather than lose it in silence (`,` needs no quotes). Same trap for `cityTypes=`, which QSettings hands back as a QStringList: read it as a QVariant, `QVariant::toString()` of a 2-entry list is EMPTY.
* **`how-use.ini`** in a group folder says how often an OPTIONAL template is used: `[use] mapPercent=` (chance it is used at all on an eligible map) + `min=`/`max=` (copies when it is), plus optional `terrains=`/`cityTypes=` filters. No file = the group is never spawned on its own, it is only picked by name.
* **`cities-types.ini`** (next to the binary, git tracked, ships empty) forces the house style of a named town — `allar=brown-city` — overriding the terrain match. An unknown folder is reported and ignored.
* **`[building] cityStyleTerrains` is ordered by DISTINCTIVENESS, and the FIRST rule covering ≥10% of the surroundings wins.** "Most tiles wins" always answered with the commonest terrain of the world (57 towns of 83 got the same style). The sample is the chunk plus ONE FULL CHUNK of margin: the chunk itself is flattened to a single terrain, so sampling it alone can only answer "the terrain the town stands on" and a shore town never saw its sea. Every shipped style is mapped to one terrain band; keywords are matched as SUBSTRINGS (`grass` also matches `grass2`), so the specific rule must come first.
* The skeleton xml gives the bot ids and their STEP TYPES (`text`/`shop`/`sell`/`heal`/`warehouse`/`fight`) and its `<a href>` links (kept: they are the bot flow); every CONTENT is regenerated per city — names, lines, shop catalogue (grows with the city level), fight teams (city monster pool + gym type at the city level).
* The generator OWNS the door wiring: it creates the missing exterior door / interior exit and always rewrites `map`+`x`/`y` (several shipped templates point at a spawn outside their interior). Exterior door object = the walkable DOORSTEP cell (the engine door tile is the collision one above it, object Y carries the -1); interior exit = bottom row, landing above it.
* It also repairs, with a warning: bot object without `type="bot"`, bot object outside the `Object` group (the ONLY group the engine reads), duplicated bot id, skin absent from `skin/` (→ role skin of settings), tileset not staged (copied into `dest/map/tileset/`).
* `template-check.py [--fix]` is the template repair tool — run it after editing `template/`. It fixes IN THE FILES: unresolved/duplicated tileset lines, missing `type="bot"`, bot objects outside the `Object` group, bots walled in or with a skin the datapack lacks, duplicated bot ids, missing door/exit objects and wrong door targets, an interior with no NPC at all, the missing `indoor` property, and the skeleton debris (`zone=`, a `backgroundsound` that does not exist, a `<bot>` with no object). `check-generated.py <dest>` validates the OUTPUT (teleports resolve and land on a walkable cell, interiors have a way out, bot ids match, no franchise wording).
* **NPC lines: `npc-slots.json`, tracked by git.** The generator writes `dest/npc-requests.json` (every text it produced + its context + its BUCKET) and READS `npc-slots.json` (staged next to the binary by CMake): bucket key → reviewed lines, picked deterministically. `python3 npcfill.py [--time-limit <min>] [--only <key>] [--check]` fills the missing buckets with the local Ollama model (`mistral-small-4:119b`) and rewrites that file only — the human reviews the git diff, rebuilds, regenerates. ~175 buckets for a world, resumable (a bucket with ≥6 lines is never asked again). NPC **names stay hand-written** (`--names` to ask anyway: a model returns names of existing games far too often). Without any bucket the maps still read well: `dialog.txt` (70 original lines) + 5-6 written lines per role. Bucket key (identical in `LoadMapBuilding.cpp` and `npcfill.py`): `<group>|<role>|<field>|<level tier>` +`|<size>` for a house +`|<element>` for a gym leader.
* **HARD RULE — never generate, recolour or modify a TILE, a tileset or a building facade.** The art is drawn by the owner; a tileset exists to be REUSED by many buildings, so adding a generated sheet per variant is wrong by design, and a hue rotation is not architecture (a purple desert house). The generator only ASSEMBLES the drawn templates. More visual variety = the owner draws a new `template/<style>/<n>/` folder; the code side is already ready for it (folders are discovered on disk). A recolour attempt was reverted for exactly this reason.
* **A town sits on ONE terrain (`[city] flatten*`).** The terrain is sampled TWICE: first with `draw=false` (the city picker only needs the per-zone height), then cities are placed, then `TerrainFlattener` (a `TerrainShaper`, installed with `setActive`) forces the height/moisure noise of each city chunk to its DOMINANT terrain — every Voronoi zone painting inside the shape is BOUND to it, so no seam survives — and ramps back to the natural noise over `flattenFalloff` tiles, the gradient restarting at the town level so no mountain wall lands on the border. `flattenShape` rectangle/circle/octagon are three ways to build ONE polygon (one distance function). Measured on the reference world: cities cut by 2+ terrains 58/83 → 0/83.
* **City/gym/cave settings:** `[city]` is per SIZE (`small\` `medium\` `big\`, index = `CityType`). Avenue path-terrain is DERIVED from `template/city-<size>.tmx` (Walkable fill = path, OnGrass 3x3 ring = border; edit the tmx to retheme; `useAsBase` brushes the tmx itself centered), `signTiles` list (one sign style per city, signs at the avenue entrances, re-asserted post-vegetation so nothing hides them). STREET-FRONT LOTS filled center-out on both avenue frontages for EVERY size (doored buildings only on the door-facing side, door-front tiles validated+reserved); big city additionally gets doorless filler facades and plaza patches.
* **The city HOLE (`[city] <size>\holePercent`) is what makes a town read as a town.** A small town laid out over its whole 44x44 chunk was one building lost in an empty field. `LoadMapAll::cityHole` is the centered rect (clamped to leave a 5-tile ring) that holds the avenue and EVERY building; `maskCityHoles` marks it in `MapBrush::mapMask` right after `initialiseMapMask` and **before the transitions**, which is what stops the outer-border pass drawing mountain COLLISION ridges across the square — the same mark then keeps vegetation out, so the trees form a FRAME around the town. The road-paint rock-border decoration is skipped inside the hole for the same reason. `<size>\densityPercent` caps the building footprint share of the hole (upper limit, denies a building that would exceed it), `<size>\minBuilding` is the count to try for excluding heal/market (best effort).
* **THE SEA IS DECIDED ON THE MAP GRAPH, then drawn on the WHOLE WORLD AT ONCE.** Two stages, and they do not mix: `LoadMapAll::addWaterPaths` (from `addCity`, the last moment the chunk graph can change) decides WHAT is linked, `LoadMapAll::addSeaContent` (`LoadMapSea.cpp`, from `main` after `addRoadContent` and before the decorations/vegetation) draws it. There is no per-chunk sea painter any more: a coast does not stop at a map border, so neither may the rock that closes it.
* **HARD RULE: A WATER PATH NEVER CROSSES LAND — a lane no more than a ferry.** A lane is drawn through WATER ONLY, from the beach of one end to the beach of the other; a ferry is only ever built between two shores sitting on the SAME BODY OF WATER (`shoreWater`, the bodies each shore map can put to sea on), so it can never sail from a lake to the ocean over a continent. The minimap draws the ferry leg TILE BY TILE through the water, FROM ONE MOORED BOAT TO THE OTHER, for the same reason — and so the line comes out between the two icons instead of hugging whichever edge of the strait is nearest.
* **A MAP DOES NOT HAVE TO TOUCH THE SEA TO PUT TO SEA.** Any map within `[water] harbourChunkRadius` of a sailable chunk is an embarkation point (`harbourOfChunk`, a BFS over LAND from every sailable chunk — a harbour on the far side of a bay is not this map's harbour), and the BRANCH between the map and its harbour is linked as ordinary ROAD maps when the link is built, so the way down to the sea is a road the road generator draws. Asking a town to touch the water is what hid the two towns facing each other across a bay: one of them is two maps inland.
* **A GROUP THE LAND CAN REACH IS JOINED BY LAND.** Before the sea is asked for anything, two groups of maps are joined by a ROAD whenever empty land runs between them: the chunks the join walks through become ordinary road maps (`generateRoadContent` paints any chunk whose orientation bits are set). That is what answers a group sitting by a LAKE and nothing else — 44 maps of the reference world, joined by 8 new road maps instead of a ferry drawn straight over the continent.
* **THE MESH (`addWaterPaths`).** 1) the maps a ROAD joins are one GROUP (connected components of `mapPathDirection`). 2) the groups are linked by their CLOSEST pair of shore maps, the group with the FEWEST links served first, until none is on its own. **WHAT A DIRECT NEIGHBOUR IS: THE LINE, not a distance comparison.** The straight line between the two maps may walk over NO MAP AT ALL — not a third group's and not their own — and **two sea links never cross** (`segmentsCross` on the chunk centres). That is what "going around another group" really means. Comparing distances instead (the relative neighbourhood graph: no third group closer to both ends) was tried and REMOVED: one big continent is closer to everything and shadows every other pair, and it threw away the two towns of a world facing each other across a bay 8 maps apart with no other water between them. Both tests are relaxed ONE AT A TIME and only for a group that would otherwise stay cut off; a relaxed pass takes the SHORTEST link, not the least connected one. Every accepted link is logged, and so is every REFUSED pair with its reason. 3) BOAT OR LANE is decided HERE, for the whole mesh: a link no continuous water can be sailed along is a boat whatever the quota says, then `[water] boatPercent` picks the rest shortest-route-first. A link whose two shores cannot MOOR A SHIP is never picked (`chunkCanMoorShip`, measured on the terrain): the quota moves to the next water path instead, which is the only way the far side does not end up with a teleport pointing at nothing. ONE crossing per harbour chunk — two ferries in one chunk silently replaced each other's teleport. The result is `waterRoutes` (the chunks of each link, land ends included) plus `boatCrossings`.
* **THE ROCK GUIDES, IT DOES NOT RING THE CONTINENT** (`closeSeaAccess`, the LAST pass of all). Two rules, and nothing else is ever drawn: (1) THE RIM — one tile of rock in the water against a shore THE PLAYER CAN REALLY STAND ON: no Collisions tile on it (a cell of the Walkable layer that also carries a tree or a cliff is not a shore) AND a way really leads there (`seaReachableCells`, flooded from the towns over the ground and the water the generator opened). Protecting the sea in front of a wood is a rock drawn for nobody: 9332 rock cells became 1118. (2) THE FRAME — the water the player may NOT use that touches water they MAY; that one never asks whether the water beside it is reached, because what was opened on purpose is one connected piece and one walkable beach opens all of it. A band of reefs ten tiles out all round the world was the first version and it was wrong twice: dashed lines floating in the open sea, and drawn against coasts nobody can reach.
* **THE ROCK IS DRAWN AFTER THE VEGETATION AND THE REPAIRS.** The trees are brushed after the sea is shaped and turn whole stretches of open coast into a wall — a rim drawn before them is a rock in front of a wood. So `addSeaContent` shapes (lanes, pools, harbours, islets, boats, content, vegetation masks) and `closeSeaAccess` draws, from `main`, after the vegetation and the townsfolk. `checkWalkability` then runs with `seaWallCells` protected AND the closed sea forbidden to its corridors (the flood walks water, so a repair happily ran its corridor over the sea and the ground it opened on the far side became a new way in), `closeSeaAccess` runs a SECOND time to close whatever those repairs opened (it only ever ADDS rock, so it is idempotent), and `checkSeaClosed` measures the result BY FLOODING THE WORLD FROM THE TOWNS the way the player moves (water fully swimmable): any water it reaches that the generator did not open is a leak, and it is fatal.
* **A POOL is the way in, and it is FRAMED.** The open sea starts closed and is opened only where a lane comes ashore (`poolSeeds`: the lane cells that touch walkable ground). From that beach the pool is grown `[water] beachMin..beachMax` tiles out — wandering, a smooth value noise (`seaNoise`, never `rand()`: this pass is world-level and a per-chunk stream would make one map's coast depend on its neighbour) — and GROWN AGAIN until it holds `[water] poolMinTiles` (200) cells, so the rock always frames a real bay. Its wall runs out into the sea, comes back and ENDS ON THE LAND at both ends of the beach; the beach itself keeps no rim, which is the way in. Movement is 4-directional, so "every non-allowed water cell touching an allowed one, or touching a walkable shore" is a closed cut by construction — one tile of rock, never a sea filled with it, never a line along a chunk border.
* **ONLY THE OPEN SEA IS EVER CLOSED.** The water is split into connected bodies on the FINAL map; a body under `[water] seaMinTiles` is a lake or a pond and is swimmable end to end. A rock chain across a mountain lake is a wall drawn for nothing.
* **A LANE is drawn from BEACH TO BEACH**, through WATER ONLY, over the chunks of its route and no others, then widened to `channelHalfWidth`. A BEACH is a water cell of the route's first (or last) two chunks that touches ground the player can stand on. When no water joins the two beaches the link becomes a FERRY on the spot rather than a lane drawn over the land. Drawing it on the world instead of chunk by chunk is what makes the two ends meet the land: a per-chunk lane stopped at a border the neighbour had walled.
* **THE WALK FROM THE WATER TO THE TOWN is opened on the WORLD, up to the nearest town** — a lane beach and a ferry quay alike. It crosses as many maps as it needs: a way opened only inside the landing chunk stops at its border and the player is still walled in. Open ground costs 1 and a wood or a cliff 60, so it follows the road already there and only cuts where it must (WHOLE plants, `MapPlants::removePlantAt`), and the whole way is vegetation-masked, so what is brushed next does not close it again. On the reference world it opens 0 cells: the road was always there.
* **A BOAT chunk is a HARBOUR, not a corridor.** Its basin stays open water so the ship has room, and the sides NO MAP lies behind are closed by a rock line `[water] boatBorderMin..boatBorderMax` (3..5) tiles inside the map border, wandering too. The ship lies HORIZONTALLY, inside the rock, and has to touch the land by the SIDE of a tile (never a corner): the berth with the most shore along its length wins, a walkable quay beating a cliff coast. **A SPRITE IS NOT A RECTANGLE**: the boat is a 4x3 BLOCK of `ships.tsx` and two of its twelve tiles are fully transparent, so `stampTileRect` skips a blank tile (`tileIsBlank`) — it used to put an invisible collision in the water beside the hull and a teleport on a cell where there is no boat. Careful with that test: this libtiled hands EVERY tile the WHOLE SHEET from `Tile::image()` (the renderer crops by id), so the tile's own rectangle has to be cropped out before looking at its alpha. **EVERY OBJECT OF THE MOVING GROUP IS WRITTEN ONE ROW DOWN**: `Map_loaderMain.cpp` reads `object_y = y/tileheight - 1` for the WHOLE group, not just for a bot, and the hand-drawn datapack writes its doors that way (`test/city.tmx`: the door object sits one row BELOW its door tile, and the exit of `house1.tmx` is at y=15 in a 15-row map). `addMapChange` and the cave objects already did it; the boat teleport did not, so every one of them acted on the row ABOVE the hull — off the boat. A push-teleport goes on EVERY SHIP TILE that qualifies, not on one of them: the player boards where they stand, and pushing at the wrong plank did nothing. A tile qualifies when the cell BESIDE it (a SIDE, never a corner) is ground the player STANDS ON: no Water tile, a Walkable tile, no Collisions — and nothing grows on a quay, it is vegetation-masked, else a tree brushed after this pass turns a plank back into one nobody can push. Water is never a quay — it needs the swim item, and the ferry is what the player takes when they have none — so a coast under a tree, on a cliff edge or with nothing drawn on it is MADE one (whole plants, and the ground of the chunk filled in). The player arrives on the QUAY of the other side, never on the boat tile, which is a collision. `check-generated.py` re-checks the same contract on the written maps.
* **A QUAY IS REACHED ON FOOT, and the water is a WALL while it is measured.** A ferry map is mostly sea, so its biggest walkable component is the basin: a quay "reachable" through the water is reachable by nobody, since the boat is what the player takes when they cannot swim. So the berth is scored on the shore the BORDER of the map really reaches on foot (`seaFootComponents`), the walk from that border to the quay is vegetation-masked like a road masks its own way (the vegetation is brushed after the sea pass and grew a wood across the shore), a quay that is a tree or a cliff edge is opened whole-plant, and `checkWalkability` rule 3 re-measures it on the final map and repairs with the WATER FORBIDDEN — without that the corridor happily "opened" a way through the harbour, clearing nothing, filling nothing, and eating a tile of the boat on the way. `check-generated.py` re-checks the same rule from the written maps (a push teleport standing on a collision ON THE WATER is a boat).
* **A border-* object is the WHOLE SIDE of the map, not a teleport on one cell** (`Map_loaderMain.cpp`: it stores the neighbour file and a `y_offset`/`x_offset`, and the generator writes an offset of 0). Every border object is written ONE ROW DOWN (the -1 object convention), so the line of a TOP border is the row ABOVE the object: reading the object row made the guard check and repair row 1 while the player crosses on row 0, and a top border could be a wall from end to end with the guard reporting nothing. A crossing needs a PAIR of cells, one on each map, at the same index — `openBorderPairs` runs first, on the world, and opens one pair per link (never a sea wall cell); the per-chunk repair then makes that pair reachable from inside its own map. A CAVE chunk is the exception: its sides are meant to be separated and each only has to reach a cave mouth.
* **NO RULER STROKE, AND NO PATTERN EITHER.** A straight rock line with ONE rock nudged out every N tiles is worse than the straight line: it reads as a stencil. So the EDGE of the swimmable water is ROUGHENED before any rock is drawn (`addSeaContent`, two passes: each cell just outside the edge is given to the water on a hash of its own position, 40%), and the rock then follows a coast of one and two tile bites. The anti-run shift stays as a safety net only, and it breaks a run where a HASH says, never on a fixed step. `checkSeaClosed` re-measures the written map and is fatal at 16 in a row. Measured outside the generator on the reference world: longest run 14, and 1384 runs of one tile against 2 runs over 8.
* **THE SEA WALL IS NEVER OPENED BY A REPAIR.** `carveChunkCorridor` and `openBorderPairs` both refuse `seaWallCells`: a corridor cut through the rock hands the player the open sea, which is the one thing it exists to stop. Verified independently by flooding `all.tmx` FROM THE TOWNS the way the engine walks it: the water reached is the ponds, the pools and the lanes, and not one step leaves a written map by water.
* **`template/sea/<name>/` is the content of a swimmable route** (`scanSeaTemplates` + `addSeaContent`), the same shape as `template/on-<terrain>/`: one tmx of REAL drawn tiles plus its `how-use.ini`. It is brushed on the open water of a LANE only (never in a harbour: a ferry chunk is a quay, the player never swims there), and only where the whole footprint PLUS a ring of one tile around it is free lane water, so it can never close the way. A FIGHT bot is placed beside it, like the lone swimmers (`[water] minFighter..maxFighter`), and `emitRoadBotsForChunk` gives both their team at split time. Nothing on the water is GENERATED any more — the islets that used to be built out of mountain tiles are gone: what floats on a sea route is DRAWN, in `template/sea/`.
* **The boat is moored ON WATER at the limit of the sea and the land** — `wireBoatCrossings` runs once both shores are painted and points each teleport at the quay the other side moored on; a crossing with only one boat is DROPPED whole, objects and landing included, else the far side keeps a teleport pointing at 0,0. `boat.png` marks the crossing on the minimap like a town icon, and the leg between the two shores is drawn dashed FOLLOWING THE WATER (a cost search over the chunks that hold sea, cheapest where there is most of it): a straight line between the shores is drawn right across the land whenever the ferry rounds a cape.
* **`[water]` SEA vs LAKE** (`LoadMapAll::detectWaterBodies`, right after the terrain is drawn): connected components of the `Water` layer; a SEA — the only thing a water path may ever be routed on — is BIG **and LONG**: at least `seaMinTiles` cells AND a bounding box whose longest side reaches `seaMinSpan` (20000 / 500). Size alone made a round inland lake a shipping lane; anything at least `lakeMinTiles` is a lake, anything smaller a puddle that is not even named. **And only `portCityPercent` of the towns may put to sea at all** (30%): every coastal town growing a harbour left the world covered in ferries. The mesh links ignore that flag — joining the groups is what the sea is for. A **PORT keeps its bay**: `TerrainFlattener::setKeepWater` leaves a sample alone when its natural height is the water band (`LoadMap::floatToHigh==0`), inside the town AND in its falloff ramp, so the sea comes into the map instead of being flattened into a field — before that not one town of the world held a single water tile. Every COASTAL town sells the items its datapack asks for to WALK ON WATER, whatever its level. COASTAL is `[water] coastalChunkRadius` (0: the town's OWN chunk holds sea) PLUS every town a sea route leaves from, so a route can always be swum — the PORT radius is a different, far wider thing and put the item in more than half the shops (35 of 62, now 11): `map/layers.xml` `<monstersCollision layer="Water" type="walkOn" item="N">`, read off the datapack with `--datapack` and configured by `[building] waterWalkItems` otherwise. Without that item the engine refuses to step on the Water layer and the sea routes cannot be swum. `[water] boatPercent` is the share of the crossings made a FERRY on purpose even when a lane could be sailed; the minimap draws the crossing itself as a dashed line in the sea-route colour, else the route read as stopping dead at the coast. `[General] terrainDebug` adds an Object layer `Terrain` with each body's OUTLINE polygon, traced on a grid DOWNSAMPLED by `bodyDebugStep`: at tile resolution a noise coastline gives over a MILLION corners (useless, and it doubles `all.tmx`). The tracer stops on the state AFTER ITS FIRST STEP, never on the one before it — the walk rarely leaves the seed heading right, so "back at the seed heading right" never came true and it looped the same ring until the guard (5162 points for an 8 point lake). Sizes are written as a human reads them (`tileCountText`: 254 tiles, 42k, 52M, 444G) and counted in 64 bits.
* **`[General] cityDebug`** writes an Object layer `City` into `all.tmx`: the hole polygon of every town plus a one-line label (name, size, level, element type, style, chunk, hole, density reached/limit, buildings placed/minimum). `report-cities.py <dest>` aggregates it — use THAT to judge town density, never a count of `house-*.tmx` (a big-city filler house is a doorless facade and has no file). `[building] cityTypeTerrains="type->terrainKeyword,..;.."` — every CITY takes the element type whose terrain keywords match its surroundings (water by the sea, stone in the mountains, plant in the grass, ice on snow...), per-type counts quota-balanced; the GYM type always matches the city type. `[building] gymTypes="type[:#color]->Mon1,..;.."` — typed gyms: part of the trainer teams from the type pool, and `tileset/gym.png` (lower parts = recolor mask at +128px) recolored per type-color into `dest/map/tileset/gym-<type>.*` (`typeXml` can point at the datapack `monsters/type.xml` for colors). `[road] cave\*` — every selected road chunk becomes a cave; NO artificial cliff is ever drawn (owner: ugly). **A chunk the SEA reaches is never a cave** (route or not): the mouth art is a cliff seen from the front, so it ended up opening onto the water, or the whole cave sat on an islet with the sea all around it. A chunk with a LEFT or RIGHT road connection is never turned into a cave: the mouth art is a cliff seen from the front, so the overworld hole only sits on a HORIZONTAL collision line (top/bottom border). Per connection, the mouth is embedded in the FIRST natural cliff on the straight approach line from the border (`entranceTile` facing bottom / `entranceTopTile` terra-19 from the top side), else a small 3x3 rock OUTCROP (the `wallTile` block) stands on the flat ground; the approach band is cleared+vegetation-masked and the surrounding terrain/vegetation seals naturally. The corridor is the separate `<chunk>-cave[-N].tmx` `type="cave"` interior: ring-only collision (overworld mountain ring `region\mountain_tile/tsx`), NEVER touches the map border; exit DOORS are push-teleports ON the cliff at the accessible EXTREMITY — top side `exitTopTile` one above a walk-up gap at the TOPMOST reachable collision, other sides `exitBottomTile` at the BOTTOMMOST (the sealed border line counts); each side connects to a RANDOM floor (crossing may require the `stairDown/UpTile` stairs, "go deeper to exit"), +2 monster levels & luck rotation per floor, `itemPercent`/`items`/`itemTile` ground items, trainers inside. The whole plan lives in `LoadMapAll::cavePlans` (decided at selection time). `[wildMonsters] <id>\name` — generated xml references monsters by lowercase NAME; `minLevel==maxLevel` collapses to `level=`. `start.xml` gets one `<start>` per city in the lowest 10% of the level range (lowest = `Normal`; others = city-name ids, active once matching profiles exist in `player/start.xml`).
