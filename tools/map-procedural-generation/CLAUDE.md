# map-procedural-generation — rules

Combine with the root CLAUDE.md. This is the **content / assembly** stage: it consumes the base terrain from `../map-procedural-generation-terrain/` (THE standalone base terrain generator) and CHUNKS its big `all.tmx` into per-map **zstd**-base64 `.tmx`, then adds cities/roads, reciprocal borders + doors, NPCs/trainers/signs, wild-encounter tables and interiors (heal / shop / gym). Full on-disk spec = `target.md`; per-datapack tile/item/skin config = `settings*.ini` + `DATAPACK-CONFIG.md`; what is left to do, and which part needs DRAWN art instead of code = `TODO.md`.

* Output is a STAGING tree at `<binary>/dest/map/main/<maincode>/` — NEVER the source datapack (`CatchChallenger-datapack/` is read-only). `cities.txt`/`dialog.txt`/`template/`/`skin/` load from the BINARY directory (CMake stages them there); settings come from `settings.ini` (or `--config settings-reference.ini`).
* **The output is ONE self-contained map LABEL: it SHIPS its own `tileset/`.** `dest/map/main/<maincode>/` is copied under `map/main/<label>/` of a datapack (`install-generated.py <dest> --datapack <dir> [--label <name>]`, label auto-detected from the run, which refuses to install while a reference escapes the label, and skips the `all.tmx` debug dump). So every written reference is `../tileset/x.tsx` — NEVER `../../../tileset/` (the datapack `map/tileset/` is read-only AND owns none of the gym/heal/shop/house sheets: that copy loaded with no tileset at all). `dest/map/tileset/` + `dest/map/main/tileset/` stay the RUN-STAGING POOL (`--datapack` fills them, `stageTemplateTileset` adds the template ones); `LoadMap::shipTileset` copies out of the pool at WRITE time, so an unused tileset is never shipped. `check-generated.py` enforces it.
* **Every CHUNK draws from its OWN random stream** (`LoadMapAll::seedChunk`, called first thing in each chunk-local pass with its `ChunkPass` id). Changing how many `rand()` a chunk consumes then shifts THAT chunk only, not the whole world — a diff stays readable and a regression stays local (measured: one extra `rand()` in one chunk touches 6 files out of 647, all of that chunk). NEVER reseed the global height/moisure/voronoi noise per chunk — it is global by construction and would tile the world. `check-determinism.py <build dir>` proves two runs stay byte identical; run it after any generator change.
* **RIGID rectangular grid-aligned features** (root + terrain CLAUDE.md): the terrain generator shapes the grass/feature zones; FILL them solid, NEVER thin a zone with per-cell noise to look "natural" (the `doc/mapping/Badmap.png` mistake — reverted once already).
* **Build/run OUT OF THE BOX:** `cmake -S . -B <build> && cmake --build <build> && <build>/map-procedural-generation` — clone, compile, run, NO argument. The `map-procedural-generation-runtime` target (always built) stages `template/ skin/ tileset/` and the txt/ini inputs next to the binary (a POST_BUILD command would only run when the binary relinks, so a template edit would never reach the build dir), and `LoadMap::stageTilesetPool` fills `dest/map/tileset/` + `dest/map/main/tileset/` from that `tileset/` at startup. Optional `--datapack <dir>` stages a datapack's tilesets FIRST, so they win over the tool's own copy of the same file name. ~32 s for 83 cities / 647 maps; repeated runs are byte identical. `[General] cleanTileset` (default true) drops the pool entries no map referenced once the run is over.
* **VERIFY by rendering** (vision): maps are **zstd** base64 (`Base64Zstandard`, everywhere: chunks, interiors, all.tmx) — a renderer without zstd shows all-black. Use a zlib tileset renderer that follows each map's own relative `<tileset source>` (they resolve inside the label, `dest/map/main/<maincode>/tileset/`). A city must read as a town (HEAL/SHOP/gym buildings, grid trees); roads carry rigid grass blocks.
* **A skinned bot must stand on a FREE cell** (no `Collisions`, no `WalkBehind` above it, no second bot): vegetation is brushed LAST, so city townsfolk are placed after it (`main.cpp`) and road bots mask a ±2 ring (`maskVegetationAround`, like the signs). A bot with NO skin is a marker on a decor tile (sign, heal machine) and is a collision on purpose. `check-generated.py` enforces it.
* **Content quality:** NPC/trainer `<name>` come from an invented neutral name pool in `botStepXml` (LoadMapRoad.cpp), NOT the numeric bot id; flavor NPC lines come from `dialog.txt` (original themed sentences, not Lorem-Ipsum). `target.md` §2.1 = the region / location / `building/` naming taxonomy (real name → type fallback `city-N`/`cave-N`/`road-N`; isolated interiors under one `building/`; multi-region split by name/graph/`region-N`).
* **NEVER any franchise wording** in a generated text nor in a `template/` skeleton: the world is ORIGINAL. Generic English words are fine (Mart, Hospital, Gym). The word list is operator-local (`~/.config/CatchChallenger/franchise-denylist.txt`, loaded by `franchise_denylist.py`) — it must NOT be committed, it is made of the very names we may not carry. `npcfill.py` filters the model output, `check-generated.py` re-checks the whole tree, `template-check.py` re-checks the skeletons (the per-city rewrite hides them otherwise). No list on the machine = check skipped with a notice.

# Building templates (`template/<group>/`)

Every city building comes from a template FOLDER, discovered on disk (`LoadMapBuilding.cpp`), never hard-coded: one exterior tmx (brushed on the city ground) + `floor-N.tmx` interiors + `floor-N.xml` **content skeleton**. A group is either one folder per variant (`sea-city/1`..`7`) or the files directly (`shop-small`).
* Groups used: `heal-{small,medium,big}` and `shop-{small,medium,big}` picked by CITY SIZE, `gym-building` (non-small cities, keeps its historical shape: the template's fight bot is the LEADER, `[building] gymTrainers` extra trainers are injected on free cells and removed from the shared template afterwards), and one `*-city` STYLE group per city for the filler houses. Output names: `heal/shop/gym/house-N.tmx`+`.xml` (multi-floor → folder + `floor-N`).
* **A city STYLE may ship its own key buildings** (`LoadMapAll::cityBuildingSet`, stem = the style folder without `-city`): `desert-market-heal` (ONE building holding both the shop and the heal bot → written as `market-heal`) beats `desert-market`+`desert-heal`, which beat `desert-market-<size>`+`desert-heal-<size>`, which beat the generic `shop-<size>`+`heal-<size>`; `desert-gym` beats `gym-building`. `desert-special-building` is spawned per its own `how-use.ini`. Nothing to declare — the folders are looked up on disk, so dropping `template/desert-market/` in is all it takes.
* **`how-use.ini`** in a group folder says how often an OPTIONAL template is used: `[use] mapPercent=` (chance it is used at all on an eligible map) + `min=`/`max=` (copies when it is), plus optional `terrains=`/`cityTypes=` filters. No file = the group is never spawned on its own, it is only picked by name.
* **`cities-types.ini`** (next to the binary, git tracked, ships empty) forces the house style of a named town — `allar=brown-city` — overriding the terrain match. An unknown folder is reported and ignored.
* **`[building] cityStyleTerrains` is ordered by DISTINCTIVENESS, and the FIRST rule covering ≥10% of the surroundings wins.** "Most tiles wins" always answered with the commonest terrain of the world (57 towns of 83 got the same style). The sample is the chunk plus ONE FULL CHUNK of margin: the chunk itself is flattened to a single terrain, so sampling it alone can only answer "the terrain the town stands on" and a shore town never saw its sea. Every shipped style is mapped to one terrain band; keywords are matched as SUBSTRINGS (`grass` also matches `grass2`), so the specific rule must come first.
* The skeleton xml gives the bot ids and their STEP TYPES (`text`/`shop`/`sell`/`heal`/`warehouse`/`fight`) and its `<a href>` links (kept: they are the bot flow); every CONTENT is regenerated per city — names, lines, shop catalogue (grows with the city level), fight teams (city monster pool + gym type at the city level).
* The generator OWNS the door wiring: it creates the missing exterior door / interior exit and always rewrites `map`+`x`/`y` (several shipped templates point at a spawn outside their interior). Exterior door object = the walkable DOORSTEP cell (the engine door tile is the collision one above it, object Y carries the -1); interior exit = bottom row, landing above it.
* It also repairs, with a warning: bot object without `type="bot"`, bot object outside the `Object` group (the ONLY group the engine reads), duplicated bot id, skin absent from `skin/` (→ role skin of settings), tileset not staged (copied into `dest/map/tileset/`).
* `template-check.py [--fix]` is the template repair tool — run it after editing `template/`. It fixes IN THE FILES: unresolved/duplicated tileset lines, missing `type="bot"`, bot objects outside the `Object` group, bots walled in or with a skin the datapack lacks, duplicated bot ids, missing door/exit objects and wrong door targets, an interior with no NPC at all, the missing `indoor` property, and the skeleton debris (`zone=`, a `backgroundsound` that does not exist, a `<bot>` with no object). `check-generated.py <dest>` validates the OUTPUT (teleports resolve and land on a walkable cell, interiors have a way out, bot ids match, no franchise wording).
* **NPC lines: `npc-slots.json`, tracked by git.** The generator writes `dest/npc-requests.json` (every text it produced + its context + its BUCKET) and READS `npc-slots.json` (staged next to the binary by CMake): bucket key → reviewed lines, picked deterministically. `python3 npcfill.py [--time-limit <min>] [--only <key>] [--check]` fills the missing buckets with the local Ollama model (`mistral-small-4:119b`) and rewrites that file only — the human reviews the git diff, rebuilds, regenerates. ~175 buckets for a world, resumable (a bucket with ≥6 lines is never asked again). NPC **names stay hand-written** (`--names` to ask anyway: a model returns names of existing games far too often). Without any bucket the maps still read well: `dialog.txt` (70 original lines) + 5-6 written lines per role. Bucket key (identical in `LoadMapBuilding.cpp` and `npcfill.py`): `<group>|<role>|<field>|<level tier>` +`|<size>` for a house +`|<element>` for a gym leader.
* **HARD RULE — never generate, recolour or modify a TILE, a tileset or a building facade.** The art is drawn by the owner; a tileset exists to be REUSED by many buildings, so adding a generated sheet per variant is wrong by design, and a hue rotation is not architecture (a purple desert house). The generator only ASSEMBLES the drawn templates. More visual variety = the owner draws a new `template/<style>/<n>/` folder; the code side is already ready for it (folders are discovered on disk). A recolour attempt was reverted for exactly this reason.
* **A town sits on ONE terrain (`[city] flatten*`).** The terrain is sampled TWICE: first with `draw=false` (the city picker only needs the per-zone height), then cities are placed, then `TerrainFlattener` (a `TerrainShaper`, installed with `setActive`) forces the height/moisure noise of each city chunk to its DOMINANT terrain — every Voronoi zone painting inside the shape is BOUND to it, so no seam survives — and ramps back to the natural noise over `flattenFalloff` tiles, the gradient restarting at the town level so no mountain wall lands on the border. `flattenShape` rectangle/circle/octagon are three ways to build ONE polygon (one distance function). Measured on the reference world: cities cut by 2+ terrains 58/83 → 0/83.
* **City/gym/cave settings:** `[city]` is per SIZE (`small\` `medium\` `big\`, index = `CityType`). Avenue path-terrain is DERIVED from `template/city-<size>.tmx` (Walkable fill = path, OnGrass 3x3 ring = border; edit the tmx to retheme; `useAsBase` brushes the tmx itself centered), `signTiles` list (one sign style per city, signs at the avenue entrances, re-asserted post-vegetation so nothing hides them). STREET-FRONT LOTS filled center-out on both avenue frontages for EVERY size (doored buildings only on the door-facing side, door-front tiles validated+reserved); big city additionally gets doorless filler facades and plaza patches.
* **The city HOLE (`[city] <size>\holePercent`) is what makes a town read as a town.** A small town laid out over its whole 44x44 chunk was one building lost in an empty field. `LoadMapAll::cityHole` is the centered rect (clamped to leave a 5-tile ring) that holds the avenue and EVERY building; `maskCityHoles` marks it in `MapBrush::mapMask` right after `initialiseMapMask` and **before the transitions**, which is what stops the outer-border pass drawing mountain COLLISION ridges across the square — the same mark then keeps vegetation out, so the trees form a FRAME around the town. The road-paint rock-border decoration is skipped inside the hole for the same reason. `<size>\densityPercent` caps the building footprint share of the hole (upper limit, denies a building that would exceed it), `<size>\minBuilding` is the count to try for excluding heal/market (best effort).
* **`[General] cityDebug`** writes an Object layer `City` into `all.tmx`: the hole polygon of every town plus a one-line label (name, size, level, element type, style, chunk, hole, density reached/limit, buildings placed/minimum). `report-cities.py <dest>` aggregates it — use THAT to judge town density, never a count of `house-*.tmx` (a big-city filler house is a doorless facade and has no file). `[building] cityTypeTerrains="type->terrainKeyword,..;.."` — every CITY takes the element type whose terrain keywords match its surroundings (water by the sea, stone in the mountains, plant in the grass, ice on snow...), per-type counts quota-balanced; the GYM type always matches the city type. `[building] gymTypes="type[:#color]->Mon1,..;.."` — typed gyms: part of the trainer teams from the type pool, and `tileset/gym.png` (lower parts = recolor mask at +128px) recolored per type-color into `dest/map/tileset/gym-<type>.*` (`typeXml` can point at the datapack `monsters/type.xml` for colors). `[road] cave\*` — every selected road chunk becomes a cave; NO artificial cliff is ever drawn (owner: ugly). A chunk with a LEFT or RIGHT road connection is never turned into a cave: the mouth art is a cliff seen from the front, so the overworld hole only sits on a HORIZONTAL collision line (top/bottom border). Per connection, the mouth is embedded in the FIRST natural cliff on the straight approach line from the border (`entranceTile` facing bottom / `entranceTopTile` terra-19 from the top side), else a small 3x3 rock OUTCROP (the `wallTile` block) stands on the flat ground; the approach band is cleared+vegetation-masked and the surrounding terrain/vegetation seals naturally. The corridor is the separate `<chunk>-cave[-N].tmx` `type="cave"` interior: ring-only collision (overworld mountain ring `region\mountain_tile/tsx`), NEVER touches the map border; exit DOORS are push-teleports ON the cliff at the accessible EXTREMITY — top side `exitTopTile` one above a walk-up gap at the TOPMOST reachable collision, other sides `exitBottomTile` at the BOTTOMMOST (the sealed border line counts); each side connects to a RANDOM floor (crossing may require the `stairDown/UpTile` stairs, "go deeper to exit"), +2 monster levels & luck rotation per floor, `itemPercent`/`items`/`itemTile` ground items, trainers inside. The whole plan lives in `LoadMapAll::cavePlans` (decided at selection time). `[wildMonsters] <id>\name` — generated xml references monsters by lowercase NAME; `minLevel==maxLevel` collapses to `level=`. `start.xml` gets one `<start>` per city in the lowest 10% of the level range (lowest = `Normal`; others = city-name ids, active once matching profiles exist in `player/start.xml`).
